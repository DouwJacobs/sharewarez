# Database migrations

GameLibrary uses Flask-Migrate and Alembic for ordered PostgreSQL schema changes.
Startup applies pending revisions before any web workers begin serving requests.
Migration failures stop startup rather than allowing application code to run
against an incompatible schema.

## Existing installations

The first migration-aware startup detects an unversioned database, runs the
legacy idempotent reconciliation once, and records revision `20260809_01`.
Once `alembic_version` exists, the legacy updater is skipped permanently and
only Alembic revisions are applied.

Back up the database before upgrading. Do not manually create or edit the
`alembic_version` table.

## Developer workflow

Activate the `sharewarez` pyenv environment and load `.env`, then use:

```bash
flask --app 'sharewarez:create_app' db current
flask --app 'sharewarez:create_app' db history
flask --app 'sharewarez:create_app' db migrate -m "describe schema change"
flask --app 'sharewarez:create_app' db upgrade
```

Review every autogenerated revision. Add data migrations explicitly, make
upgrade behavior safe for populated databases, and provide a non-destructive
downgrade where practical. Commit model and migration changes together.

Production containers apply upgrades automatically. Operators can inspect the
current revision with `flask db current` inside the application container.
Revision `20260809_03` adds optional one-level collection grouping and collection artwork URLs. Existing collections remain top-level and require no data conversion.

Revision `20260905_25` repairs missing search extension/indexes on metadata-created
schemas that were stamped without historical non-model DDL. Fresh bootstrap runs
this immutable revision before stamping. It also adds GiST title-distance indexes
for bounded global-search candidates. Startup must complete this migration before
serving revised search traffic. Normal upgrades acquire index creation locks;
allow a maintenance window on large catalogues. Downgrade retains repaired search
objects and removes only the added distance indexes.

Revisions `20260922_26` through `20260922_29` add provider-neutral game and request
identities, encrypted RAWG configuration, request attribution, and provider-aware
relationship/image provenance. Existing IGDB rows are backfilled in place. Legacy
IGDB columns remain for compatibility, and old local metadata files need no rewrite.

Revision `20261105_33` adds durable scan attempt links, options, a nullable outcome
and an unmatched counter. It preserves existing status enum values and populated
rows. Its upgrade also recognizes metadata-created columns, indexes and foreign
keys, and its downgrade recognizes PostgreSQL-generated FK names. Fresh schema,
previous-version populated upgrade, downgrade/re-upgrade, and a single revision
head are covered by `tests/test_migrations.py`. Follow the normal backup and
Alembic upgrade procedure before running code that uses these fields.

Revision `20261106_34` adds nullable transfer evidence after `20261105_33`:
terminal reason, delivery kind, original expected response bytes, correlation ID,
nullable administrator actor with SET NULL, and a timezone-aware progress clock.
Existing attempts are preserved with null evidence; no cause is inferred. The
revision handles both previous populated schemas and metadata-created columns/FKs.
Tests cover fresh bootstrap, populated upgrade, downgrade/re-upgrade, an 8 GB
expected length, actor deletion and one migration head. Follow the usual backup
and Alembic upgrade process before starting code that reads these fields.
